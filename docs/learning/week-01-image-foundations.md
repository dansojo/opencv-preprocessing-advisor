# 1주차 — 이미지 표현과 색 공간

매일 공통 시간: **5분 회상 + 10분 개념/코드 + 10분 실험 + 5분 말로 설명**. 입력은 BGR `uint8` 배열이라는 프로젝트 계약에서 출발합니다. [I/O 구현](../../src/opencv_preprocessing_advisor/io.py)을 옆에 두세요.

## Day 1 — NumPy 이미지 배열

시간: **5분 회상 + 10분 개념/코드 + 10분 실험 + 5분 말로 설명**

### 목표
이미지를 `(높이, 너비, 채널)` NumPy 배열로 읽고 픽셀 하나를 숫자로 설명한다.

### 개념
OpenCV의 컬러 이미지는 보통 3차원 배열이다. 좌표는 `image[y, x]` 순서이며, 값의 범위와 자료형을 먼저 확인해야 연산 결과를 해석할 수 있다.

### 코드 연결
[입력 검증](../../src/opencv_preprocessing_advisor/io.py)과 [배열 계약 테스트](../../tests/test_io.py)를 읽고, 어떤 shape를 허용하는지 표시한다.

### 실습
임의의 `np.zeros((4, 5, 3), dtype=np.uint8)`를 만들고 shape, dtype, `(0, 0)` 픽셀을 출력한다. 한 채널에 300을 넣으려다 왜 문제가 되는지 메모한다.

### 말로 설명
“이미지는 숫자 배열이며, 전처리 전에는 shape·dtype·채널 순서를 확인해 잘못된 연산을 막는다”라고 45초간 말한다.

## Day 2 — dimensions, shape, dtype

시간: **5분 회상 + 10분 개념/코드 + 10분 실험 + 5분 말로 설명**

### 목표
shape와 dtype이 결과의 범위·메모리·OpenCV 호환성에 주는 영향을 구분한다.

### 개념
`uint8`은 0~255 범위를 표현하지만, 더하기·빼기에서 포화나 형 변환을 의식해야 한다. float 계산 후 `uint8`로 바꾸는 위치도 결과를 바꾼다.

### 코드 연결
[normalize_uint8](../../src/opencv_preprocessing_advisor/transforms.py)와 [변환 테스트](../../tests/test_transforms.py)에서 반환 dtype을 확인한다.

### 실습
`uint8` 배열과 `float32` 배열에 같은 밝기 연산을 적용해 최소·최대값을 비교한다. 변환 직전/직후 dtype을 표에 기록한다.

### 말로 설명
“dtype은 저장 형식만이 아니라 산술 결과의 해석 조건”이라고 말하고, `uint8`을 그대로 쓰면 조심할 한 가지를 든다.

## Day 3 — BGR과 Gray

시간: **5분 회상 + 10분 개념/코드 + 10분 실험 + 5분 말로 설명**

### 목표
BGR 순서와 회색조 변환의 정보 손실을 설명한다.

### 개념
OpenCV 기본 컬러 순서는 RGB가 아니라 BGR이다. Gray는 밝기 정보를 한 채널로 요약하므로 색 구분이 필요한 문제에는 그대로 대체할 수 없다.

### 코드 연결
[apply_gray_bgr](../../src/opencv_preprocessing_advisor/transforms.py)와 [색 변환을 쓰는 진단](../../src/opencv_preprocessing_advisor/diagnostics.py)을 읽는다.

### 실습
같은 BGR 배열을 Gray로 바꾼 뒤 3채널로 다시 바꾼다. 원본과 재확장 결과가 왜 다를 수 있는지 픽셀 세 개로 비교한다.

### 말로 설명
“Gray는 계산을 단순하게 하지만 색차를 버린다. 그래서 목적이 밝기·경계인지 색 분류인지 먼저 묻는다”라고 말한다.

## Day 4 — HSV

시간: **5분 회상 + 10분 개념/코드 + 10분 실험 + 5분 말로 설명**

### 목표
HSV의 H·S·V를 색상 분리 문제에 연결한다.

### 개념
HSV는 색상(H), 채도(S), 밝기(V)를 분리해 생각하기 편한 표현이다. 하지만 OpenCV의 H 범위는 일반적인 0~360도 표기와 같지 않으므로 코드 범위를 확인해야 한다.

### 코드 연결
[ColorHistogramExtractor](../../src/opencv_preprocessing_advisor/features.py)에서 HSV 히스토그램을 계산하는 채널과 범위를 읽는다.

### 실습
파란색·회색·어두운 색 BGR 픽셀을 HSV로 변환해 H/S/V를 표로 적는다. 밝기만 낮췄을 때 어떤 값이 주로 변하는지 관찰한다.

### 말로 설명
“HSV는 색상과 밝기를 분리해 색 분포를 요약할 때 유용하지만, 채널 범위는 라이브러리 규칙을 따라 확인한다”라고 말한다.

## Day 5 — LAB

시간: **5분 회상 + 10분 개념/코드 + 10분 실험 + 5분 말로 설명**

### 목표
LAB의 L 채널을 이용해 밝기 보정을 색 정보와 분리하는 이유를 말한다.

### 개념
프로젝트의 CLAHE는 LAB으로 변환한 뒤 L(명도) 채널만 보정하고 a/b 색 성분을 다시 합친다. 이는 채널별 BGR 보정과 다른 선택이다.

### 코드 연결
[apply_lab_clahe](../../src/opencv_preprocessing_advisor/transforms.py)와 [선택 근거](../portfolio/case-study.md)를 나란히 읽는다.

### 실습
색이 있는 간단한 이미지에 BGR 채널별 equalization과 L 채널 CLAHE를 각각 적용한다. 색이 달라 보이는 위치를 하나 기록한다.

### 말로 설명
“L만 보정하면 밝기 대비 개선과 색 성분 보존을 분리해 다룰 수 있다. 다만 항상 더 낫다고 단정하지 않고 비교한다”라고 말한다.

## Day 6 — Unicode 안전 I/O

시간: **5분 회상 + 10분 개념/코드 + 10분 실험 + 5분 말로 설명**

### 목표
비ASCII 경로에서 이미지 읽기·쓰기를 검증하는 이유를 이해한다.

### 개념
파일 경로는 이미지 배열과 별개의 경계 조건이다. 프로젝트는 경로를 바이트로 읽어 OpenCV 디코더에 넘기는 방식으로 Unicode 경로를 다룬다.

### 코드 연결
[decode_image](../../src/opencv_preprocessing_advisor/io.py)와 [Unicode I/O 테스트](../../tests/test_io.py)를 읽는다.

### 실습
`한글_이미지.png`라는 임시 경로에 작은 이미지를 저장·읽기 한다. 실패하면 운영체제·라이브러리·경로 중 어디를 먼저 확인할지 적는다.

### 말로 설명
“I/O는 모델 이전의 계약이다. 경로가 깨지면 후속 진단과 전처리가 모두 무의미하므로 테스트로 경계를 고정한다”라고 말한다.

## Day 7 — 주간 복습과 미니 구현

시간: **5분 회상 + 10분 개념/코드 + 10분 실험 + 5분 말로 설명**

### 목표
이미지 검사기를 빈 파일에서 재구현하고 입력 계약을 설명한다.

### 개념
이번 주의 순서는 읽기 → shape/dtype 확인 → BGR/Gray/HSV/LAB 비교 → 관찰 기록이다. 결과 이미지보다 재현 가능한 확인 절차가 산출물이다.

### 코드 연결
[I/O](../../src/opencv_preprocessing_advisor/io.py), [색 특징](../../src/opencv_preprocessing_advisor/features.py), [입력 테스트](../../tests/test_io.py)를 다시 참조한다.

### 실습
10분 안에 파일을 읽어 shape, dtype, Gray 평균, HSV 평균, LAB L 평균을 출력하는 함수를 작성하고 실행한다. 출력 세 줄에서 색 공간별 관찰을 한 문장씩 기록한다.

### 말로 설명
“프로젝트의 모든 변환은 검증된 BGR 배열에서 시작한다”는 문장으로 1분 요약을 녹음하고, BGR과 RGB를 혼동하지 않았는지 듣는다.
